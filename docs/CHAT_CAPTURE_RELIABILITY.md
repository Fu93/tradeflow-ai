# 多供應商聊天擷取與等待狀態

此輪先用真正的 Chrome MV3 擴充功能與虛構聊天頁重現問題，再補回歸情境。平台 fixture 不等於已登入實站驗證，微信桌面版也不在 Chrome 擴充功能可讀取的範圍。

## 已重現的問題

- 兩家供應商位於同一路徑、不同 conversation query，報相同價格時，只匯入其中一家。
- 訊息到達後在 debounce 期間切換聊天室，舊訊息被歸到新的供應商。
- 舊觀察器僅讀直接新增的節點，框架巢狀新增、延後填字或替換訊息列表可能漏讀。
- 自動匯入失敗時缺少持久化待送內容；Chrome worker／瀏覽器重啟可能遺失尚未送達後端的擷取。
- 全局供應商手動選項不足以保存不同聊天室的人工對應。
- 全局草稿歷史截斷可能隱藏較安靜供應商的現行草稿。

## 修正後的契約

辨識依據包含伺服器、交易、完整聊天室網址、店名／聯絡人，以及可取得的平台訊息 ID。相同價格不代表同一家或同一則訊息。身分在收到內容時固定，不能在切換聊天後讀取新標題回填。無法唯一對應時保留待處理，不隨便指定第一家。

只有收到側的訊息才自動擷取，買方自己的訊息不參與供應商價格。原文進後端 review；規則讀取器與已設定的模型提供候選，人工確認供應商自己的單價後才參與還價計算。

自動擷取先保存在本機佇列，再送到後端。HTTP 請求有期限；等待網路的工作與保存新訊息分開，避免一家請求拖住其他家的本機保存。重試沿用同一識別；新交易或伺服器不會接收到舊交易的待匯入內容。佇列有容量限制並顯示失敗，可檢視原文、手動重試與移除。

每家顯示自己的對話狀態。沒有回覆不等於拒絕；慢回覆不阻塞其他供應商。只有有傳送證據的訊息才開始顯示等待回覆；純核准仍標示未傳送。價格、內容或對象改變後必須重新審閱正確版本，不把一次核准當成未來全部訊息的授權。

目前每筆交易仍依既有設定接受 4 或 5 家。這是建立交易規則，不是已證明的瀏覽器或線上容量上限。

## 驗證範圍與操作

`tests/test_chat_multisupplier.py` 使用真實 MV3 worker、content script、擴充功能儲存與真實本機 HTTP 後端。只有頁面 HTML 是虛構 fixture，沒有登入供應商、寄信、傳送聊天或呼叫付費模型。涵蓋同價多家、切換聊天、兩個 Chrome 視窗、較晚回覆、巢狀／漸進文字、列表替換、買方訊息排除、人工綁定、瀏覽器重啟、錯誤金鑰與已提交回應遺失。

`tests/test_supplier_threads.py` 驗證核准不等於傳送、等待一家時另一家仍可確認報價，以及忙碌供應商的歷史不會藏掉其他家的現行草稿。可重跑：

```bash
python -m playwright install chromium
python -m pytest tests/test_chat_multisupplier.py tests/test_supplier_threads.py -q
```

正式平台目前仍需以真實帳號核對 DOM、登入限制、iframe 與實際訊息 ID。聊天自動傳送尚未實作；必須另接支援的發送介面並確認結果。部署與持久磁碟按使用者要求延後，不能把本機或 CI 結果當成線上部署驗收。
