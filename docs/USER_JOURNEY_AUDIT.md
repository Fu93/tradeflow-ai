# 使用者流程除錯紀錄（2026-10-29）

本輪以 Chromium 實際操作本機應用，使用虛構供應商；停用付費模型、網路搜尋、收信與 SMTP。測試覆蓋桌面與 390px 手機畫面，以及刻意延遲或失敗的 HTTP 回應。這些結果不代表線上 Render 已部署，也不代表真實郵件或模型供應商已通過端到端驗證。

## 發現與修正

| 操作情境 | 原本的問題 | 修正後行為 |
| --- | --- | --- |
| 送出報價後輸入下一份 | 前一份回應把新文字、運費等欄位清掉 | 只有整份輸入仍與已送出內容相同才清除 |
| 等待回應時按 New deal | 舊 POST 回應重新打開舊看板 | 畫面切換會使舊回應失效；舊交易仍留在資料庫 |
| 重複按開啟、加入、確認 | 可能重複新增交易或報價 | 加入請求鎖、按鈕等待狀態與逐筆審核鎖 |
| 舊輪詢晚於確認操作回來 | 舊快照把已確認內容倒退回待確認 | 輪詢與修改分開追蹤；修改期間與之前取得的輪詢結果不套用 |
| 看草稿、選字、操作下拉選單時輪詢 | 每兩秒重建 DOM，選取、焦點或操作訊息消失 | 資料未變動時保留對應區塊與元素 |
| 已開交易的金鑰失效 | 金鑰欄位藏在建立表單，恢復操作容易建立另一筆交易 | 金鑰欄位與重新連線獨立顯示；恢復原交易 ID |
| 儲存的交易不存在 | 舊看板與失效 ID 留在頁面／儲存空間 | 停止輪詢、清除失效 ID，顯示建立新交易的提示 |
| 誤記供應商 walk-away | 後端能 reopen，介面卻沒有入口 | 供應商卡可經人工確認重新開啟；歷史仍保留 |
| 瀏覽器拒絕剪貼簿權限 | Copy draft 無反應且無提示 | 顯示成功訊息；失敗則選取草稿並提示手動複製 |
| 無 SMTP 的展示環境核准 | Approve and send 與實際只記錄核准不一致 | 後端提供當前傳送政策；按鈕與確認文字明示只核准、不寄信 |
| 伺服器要求簽章核准 | 使用者按下後才收到拒絕錯誤 | 停用不支援的瀏覽器核准，說明需使用簽章流程；可照常複製草稿 |
| 清空自訂先驗後儲存 | 空白欄位未送出，原設定無法從 UI 重設 | 對可重設的先驗欄位明確送 null，恢復已標示的政策 |
| 重新整理已啟用模擬報價的交易 | 勾選狀態與儲存政策不同，下次 Save 會意外改回 | 第一次載入從快照還原勾選狀態，使用者正在編輯時不覆蓋 |

## 可重跑的驗證

```bash
python -m playwright install chromium
python -m pytest tests/test_desk_user_journeys.py -q
python -m pytest tests -q --cov=src.desk --cov=src.engine.decision \
  --cov=src.engine.reserve --cov=src.engine.hazard_fit \
  --cov=src.engine.bilingual --cov-fail-under=90
python -m ruff check src/desk
python -m mypy
python verify_all.py
```

瀏覽器回歸測試會啟動隔離的本機 uvicorn 與暫存資料庫，故意保留前一份回應、重複提交、注入 401／404／503 與剪貼簿錯誤。簽章政策的 UI 案例注入政策快照；真正簽章驗證仍由既有後端測試負責。SMTP 未啟用，核准案例會確認顯示 `approved here, not transmitted`。
